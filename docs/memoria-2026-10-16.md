## 3. Starting state and error diagnosis

The earlier guided notebook included old preparation history and a failed server
attempt. The relevant failure was:

```text
AttributeError: '_IncludedRouter' object has no attribute 'path'
```

The HTTP instrumentation attempted to inspect a routing object using the older
attribute assumptions. The `/health` endpoint returned HTTP 500, so that server
could not be treated as a working model service. Allocated GPU memory alone did
not establish HTTP health or evaluation readiness.

Primary-source reports helped identify the dependency boundary:

- [Instrumentation issue](https://github.com/trallnag/prometheus-fastapi-instrumentator/issues/370).
- [Related vLLM issue](https://github.com/vllm-project/vllm/issues/45597).

The repair pinned **FastAPI 0.136.3** in `requirements-gpu.txt`. A new script,
`scripts/check_server_http.py`, constructs a small FastAPI app with a router and
Prometheus instrumentation, then checks health and metrics using the test client.
It verifies that HTTP integration without loading model weights.

The GPU installer was updated to run this check after dependency validation.
A separate temporary local environment passed the HTTP check and `pip check`.
The full project suite at that checkpoint passed 27 tests. Those local checks
were preparation evidence; they were not the real Gemma evaluation.

## 7. Generated correction and verification

```diff
--- a/fastapi/security/utils.py
+++ b/fastapi/security/utils.py
@@
-    return scheme, param
+    return scheme, param.strip()
```

The parser already split the authorization header. The correction normalises the
parameter's surrounding whitespace while preserving the scheme. The evaluator
accepted the resulting patch and reported `resolved: true`, verification exit 0.
The full evaluator test directory was not preserved, so this report does not
invent a count of hidden or sandbox verification tests.

Several experimental API and environment warnings were nonfatal. In particular,
a later health request failed after completion because the server had already
been cleaned up. That post-completion connection failure was not the cause of a
failed task; the recorded evaluation had completed successfully.
